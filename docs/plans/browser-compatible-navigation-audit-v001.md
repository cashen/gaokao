# 全站浏览器兼容性审计整改计划 v001

## 目标

修复 Android 浏览器（重点是 Alook 的严格/延迟点击场景）下跨模块入口“不好打开或点了无反应”的结构性风险，并统一站内旧地址，新增可公开查看的全站审计报告页。

本计划基于 2026-08-30 的全站审计记录、首页/专业路径/同学你好/招生变化页的浏览器检查，以及用户提出的“全站、Android、Alook、断网可恢复”要求。

## 已确认的风险

1. `ln-rank` 动态生成的“专业升学路径”和“大学生说专业”入口是没有 `href` 的 `button`。它们依赖全局手势事务拦截器，在原生选择器、倒计时/布局变化、Alook 的点击事件顺序下可能被拦截后没有可用的浏览器默认回退。
2. 站内仍有多个 `.html` 别名和隐式重定向；`/zy2026.html` 与 `/zy2026/index.html` 目前加载不同版本运行时，存在重复入口与资源身份分裂。
3. 历史诊断入口和 `Public_company/source` 暴露了旧入口/旧资源错误，需在不触碰受保护 `/fenxi/` 的前提下明确归并。
4. 跨模块上下文 URL 偏长；本阶段至少加入长度预算与断网/降级保护，避免把可打开性绑定在单一网络请求或过长地址上。

## 执行阶段与逐步验收

### 阶段 0：计划与续作能力

- 本文件写入 PR。
- `.codex/progress/browser-compatibility-audit-v001.json` 记录分支、基础 SHA、当前提交、阶段、测试和阻塞原因。
- 每次继续前先读取该检查点并重新核对 GitHub 分支、PR、工作流和生产状态。
- 禁止修改 `/fenxi/`、`functions/fenxi/`、`functions/_middleware.js`。

验收：Draft PR 可见；检查点可被下一次会话读取。

### 阶段 1：入口原生化与断网安全

- 跨模块动态入口改为带真实 `href` 的原生链接，并保留现有导航事件记录/返回状态能力。
- 全局交互事务只在需要时增强链接，不阻断带 `href` 的原生默认行为。
- 目标页在无网络/资源未完成时仍能依靠 URL 中已有上下文打开；不把跳转成功绑定到异步请求。
- 复核专业路径、大学生说专业、学校专业卡、专业聚合卡四类入口。

验收：静态契约测试；PC/Pad/Android Chrome 预览检查；Alook 真机检查项记录为必须人工完成，不以 CI 冒充。

### 阶段 2：站内地址归一

- 为当前入口选择唯一规范地址，并为旧 `.html` 地址保留单跳转兼容。
- 统一首页、同学你好、AIPLuS、选科/志愿工作台、招生变化页中的用户可见链接。
- `/zy2026/` 只保留一个当前运行时身份；旧根文件只作为兼容别名，不再被主动链接。
- 不删除稳定兼容资源，不新增第二套业务真相或导航状态机。

验收：重定向/规范链接扫描；每个旧入口最多单跳；当前入口资源版本一致。

### 阶段 3：审计报告页与人话说明

- 新增规范地址 `/browser-audit/`。
- 报告页公开展示：已查范围、发现、整改进度、PC/Pad/Android Chrome/Alook 验收矩阵、已知限制与回归清单。
- 页面沿用现有暖色、移动优先的家庭决策界面语言；不把工程术语作为普通用户的主叙事。
- 在全站更新记录中加入入口，方便用户与维护者找到报告。
- 明确“不宣称已经通过 Alook 真机”，直到真实设备回填证据。

验收：页面静态检查、移动布局检查、页面资源/规范地址检查、人话文案审计。

### 阶段 4：发布身份与质量门

- 以 `shared/resources/release/current-release.js` 为唯一发布 owner；本 PR 注册并推进 `browser-compatibility-audit-v001` 的 `r002` 能力修订，同时保留全站当前一致的 `v3.9.90.3 / v3990_3`。只有完整 active generation graph 可以同时迁移时才升级全站 generation，本 PR 不制造半迁移。
- 更新受影响的 active generation、缓存/资源/发布契约及对应查询串；不修改历史非 owner 版本标记。
- 增加专门的浏览器兼容审计静态契约门，确保以后不会重新生成无 `href` 的跨模块入口、重复规范地址或无报告页状态。
- 解决/分类 bounded-fanout 当前 `push + failure + jobs=[]` 的 CI 配置门；不能将其默认为产品失败，也不能带着未解释的 required failure 合并。

验收：源代码、架构、人话文案、树完整性、相关现有回归、PR Preview exact-head 全部通过。

### 阶段 5：最终发布与全站复核

严格按以下顺序：

1. Draft PR → 计划与阶段 0 检查通过。
2. 每个阶段提交后等待该阶段测试，失败则记录原因与修复提交。
3. exact-head Preview；固定预览 SHA。
4. Preview 行为检查：PC、Pad、Android Chrome；Alook 由真实设备完成并记录证据。
5. 标记 Ready；同一 SHA 的 required checks 再次全绿。
6. 使用 `expected_head_sha` 合并到 `main`。
7. 合并后核对 main SHA、树文件数、关键 CSS MIME、运行时/API、数据 SHA、Pages/自定义域名。
8. 在生产上重测首页、专业路径、同学你好、学校/专业聚合、AIPLuS、选科池、招生变化、审计报告和旧地址跳转。

## 断网/中断恢复协议

- 任何网络写入前先重新读取本检查点和分支头；失败写入不得盲重试。
- 当前提交 SHA、PR head SHA、工作流 run 与结论必须以 GitHub 实时状态为准。
- 若会话中断，从 `pending` 的第一项继续；已完成阶段不重复写入。
- 若 PR head 改变，旧 Preview/Ready/merge 证据全部失效，回到 exact-head Preview。
- 若生产部署完成但浏览器证据未完成，状态保持 `in_progress: production-browser`，不得宣称完成。
- 若 Alook 真机不可用，保留明确阻塞，不把桌面 Chrome 或 Android Chrome 结果改写为 Alook 结果。

## 受保护边界

本 PR 不修改：

- `/fenxi/`
- `functions/fenxi/`
- `functions/_middleware.js`

本 PR 保留 `functions/_lib/release-contract.js` 的两个兼容导出，并保留已声明的稳定兼容资源。

## 完成定义

只有同时满足以下条件，才可以合并：

- 计划、报告页、续作检查点已在 PR；
- 所有实现阶段均有对应测试结果；
- exact-head Preview 和同 SHA required checks 全绿；
- 未引入新的重复 owner/运行时/真相源；
- Alook 真机已完成，或用户明确接受将其作为合并后的独立人工验收（默认不接受静默跳过）；
- 合并后 main 与生产精确 SHA、全站浏览器路径复核通过。
