# ln-rank 全专业意图查询与人类口语适配 v001

## 任务边界

本 PR 不是只为“机、机械、计算机、电气、医学”等示例词增加别名，而是重构 ln-rank 的专业理解合同，覆盖当前可用专业目录中的全部约 800 个本科专业及其专业类、招生大类、学科门类和常见口语表达。

“机、机械、计算机”等只作为验收样例，不作为实现范围边界。新增专业、改名专业、带 T/K 专业、学校自定义招生大类和跨专业组合必须通过同一套专业意图解析流程。

## 用户问题

当前存在语义层级错位：

- 输入“机械”容易被提前收敛为“机械工程”一个专业；
- 输入“机”可能把机械、计算机、材料等结果混在一起；
- 输入“计算机”容易只得到“计算机科学与技术”，没有体现家长通常理解的计算机与信息方向；
- “机械类、计算机类、电子信息类、工科、工学、一级学科机械工程、师范、医学”等表达没有被统一区分；
- score-bands、major-all、major-history 和学校内专业查询可能对同一输入采用不同匹配逻辑；
- 原始字符串包含匹配可能把一个宽词扩展为不可解释的大结果集。

## 产品目标

专业查询必须同时支持：

1. 具体本科专业：精准查询；
2. 专业方向：按核心专业集合查询，并可展开相关方向；
3. 专业类/招生大类：先解释范围，再选择或按类查看；
4. 学科门类、一级学科和家长口语：识别层级并给出下一步选择；
5. 多专业：每个专业意图独立确认，最后统一查询；
6. 全部专业：不能因目录未进入预置别名表而丢失，不能只覆盖少量热门专业。

原有位置分组文案必须保持：

- 稍高目标；
- 主要参考；
- 低分侧补充。

本 PR 的页面、接口、测试和文档不得使用“冲稳保”作为用户文案。

## 专业层级合同

解析器必须显式返回以下层级之一：

```text
exact-major        具体本科专业
direction          专业方向
major-class        本科专业类
admission-group    学校招生大类/组合
discipline         学科门类或一级学科理解
broad-field        过宽领域，需要继续选择
unknown            无法安全确认
```

本科投档数据、研究生学科口径和学校招生大类必须分开。不能把研究生一级学科直接冒充本科投档专业，也不能把学校招生大类静默替换成某一个本科专业。

## 全专业意图资源

新增统一专业意图资源，资源以标准专业目录为基础，覆盖全部约 800 个本科专业，并允许按版本维护新增专业、改名专业和停招/目录变化。

每个方向意图至少维护：

```js
{
  intentKey,
  label,
  aliases,
  level,
  coreMajorCodes,
  relatedMajorCodes,
  categoryCodes,
  disciplineKeys,
  defaultScope,
  warning,
  sourceVersion
}
```

核心专业、相关方向、专业类和招生大类必须可追溯到标准代码或受控目录关系，不能依靠维护人员手工写一组模糊字符串。

## 人类输入规则

### 具体专业

输入完整专业名称或专业代码时，只查对应专业：

```text
机械工程
机械电子工程
计算机科学与技术
网络空间安全
080201
```

### 专业方向

输入“机械、计算机、电气、医学、师范、材料”等方向词时，先显示方向理解：

```text
核心专业
相关方向
包含该方向的招生大类
```

默认只查核心专业；用户选择后再扩大到相关方向或招生大类。

### 过宽词

输入“机、工科、工学、理科、医学”等过宽词时，不直接请求数百条混杂结果，而是展示可理解的方向选择。

例如“机”应给出机械与智能制造、计算机与软件、机器人与自动化、机械电子等候选；“工科”应先给出计算机信息、电气自动化、机械制造、材料化工、土木建筑、航空航天等方向。

### 专业类

输入“机械类、计算机类、电子信息类”等时，显示该专业类包含的本科专业，并提示专业类不等于单一专业。

### 学科门类/一级学科

输入“一级学科机械工程”等表达时，展示“按本科专业方向查看”的转换提示，并明确本科投档记录与研究生学科理解的边界。

### 口语、简称和变体

统一支持：

- 同义词、简称、常用口语；
- 全角/半角、空格、顿号、斜杠、和/与/及/或；
- 专业代码；
- 新目录专业、带 T/K 专业；
- 学校招生大类中包含多个专业的组合名称；
- 多专业输入与逐个确认。

单字输入不得直接作为高置信度精准专业；无法安全判断时必须停在候选选择层。

## 统一解析返回结构

前端和后端共用同一返回合同：

```js
{
  rawInput,
  terms,
  intentKey,
  intentLabel,
  intentLevel,
  status,
  coreMajorCodes,
  relatedMajorCodes,
  categoryCodes,
  selectedScope,
  matchedTerms,
  warnings,
  sourceVersion
}
```

推荐状态：

```text
ready
needs-choice
too-broad
unresolved
```

score-bands、major-all、major-history 和学校内专业入口必须使用同一解析结果，禁止入口各自维护一套关键词扩展。

## 查询匹配顺序

后端匹配顺序固定为：

1. 标准专业代码；
2. 标准专业名称；
3. 专业类代码；
4. 专业意图代码；
5. 受控别名；
6. 相关方向；
7. 原始文本模糊搜索兜底。

原始字符串包含匹配不得作为主要业务逻辑。

每条记录必须标注出现原因：

```text
精准专业
核心方向
相关方向
招生大类包含
专业类匹配
用户输入别名
```

## 交互要求

输入专业后展示“系统理解”，而不是只显示一个候选名。

支持三个低复杂度范围动作：

```text
核心专业
核心 + 相关方向
包含招生大类
```

候选未确认时不得查询；已确认专业显示为可删除标签；支持“再添加一个专业”；保留“机械/测控/材料”等快捷输入，但不能替代显式确认流程。

## 三年数据和趋势边界

只有同校、同专业、同项目可严格比较 2024、2025、2026。

招生大类发生组合变化、专业名称变化或记录不完整时，必须显示“数据不完整，不能判断三年趋势”，不得把方向集合合并成虚假趋势。

## 与现有位置、地区和学校标签兼容

- 保留“稍高目标 / 主要参考 / 低分侧补充”；
- 位置分组仍以 2026 累计位次为主，不因专业方向扩展改变分组内核；
- 地区筛选与专业意图独立组合，支持沈阳、大连及多城市并集；
- 985、211、双一流高校、双一流学科、公办/民办等继续作为事实标签；
- 双一流高校与双一流学科不可混成同一个学校层级标签。

## 最低验收矩阵

必须覆盖全部专业目录，而不只验证示例：

```text
每一个标准本科专业名称
每一个标准专业代码
每一个专业类
每一个已识别招生大类
每一个方向意图
每一个受控别名
```

重点人类输入包括但不限于：

```text
机、机械、机械类、机械工程、机械电子、机电
计算机、计算机类、网络安全、信息安全、网络空间安全
电气、自动化、电子信息、电子信息类
工科、工学、理学、医学、师范、教育
一级学科机械工程、一级学科计算机科学与技术
专业代码、简称、多个专业组合、带项目名称的招生大类
```

验收标准不是“每个词都有结果”，而是：系统能正确理解用户范围，精准专业、相关方向、专业类和招生大类不混淆，无法安全判断时不会强行查询，并且所有入口对同一输入保持一致。
